> 这是一篇示例文档，用来展示"文档"页面的写法。换成你自己的内容即可。

## 目标

需要一个能长期维护的个人站点：

- 内容用 Markdown 写，不要 CMS
- 不引入框架，三年后还能构建成功
- 推送到 GitHub 就自动发布

## 结构

```
content/            内容（纯 Markdown，带 frontmatter）
  timeline/         时间轴条目，一条一个文件
  notes/            文档，一篇一个文件
  about.md          关于页
src/
  build.mjs         构建脚本
  markdown.mjs      Markdown 渲染
  styles.css        样式
docs/               构建产物（GitHub Pages 从这里发布）
```

## 关键决策

### 为什么不用现成的框架

试过几个主流方案，问题都出在**依赖会腐坏**：三年后 `npm install` 大概率失败。

零依赖的代价是要自己写 Markdown 渲染，但那部分代码只有两百行，而且**永远不需要升级**。

### 怎样验证 AI 写的代码

三个阶段：

1. **先让它解释**：让它先描述打算怎么实现，我判断思路对不对
2. **小步构建**：一次只加一个页面，构建一次，用浏览器看一次
3. **边界检查**：故意写坏 frontmatter、放空目录、写非法链接，看它怎么崩

第 3 步最能暴露问题——AI 写的代码在"正常路径"上几乎总是对的。

## 部署

GitHub Actions 里三步：检出、构建、上传 artifact。Pages 的 source 选 "GitHub Actions"，之后每次 push 自动发布，不需要手动跑任何命令。

## 花了多久

- 讨论需求与结构：约 40 分钟
- 写构建脚本和样式：约 3 小时（其中一半在调样式）
- 配置部署：约 20 分钟

**如果全靠自己写**，同样的东西大概需要两到三天。省下的时间主要来自：不用查 CSS 兼容性、不用从零设计版式、不用回忆 Actions 的语法。

但有一件事 AI 替不了：**决定删掉什么**。初版有搜索、标签页、深色模式切换按钮，最后全砍了——因为它们增加维护成本，却不增加"别人看懂我在做什么"的效率。
